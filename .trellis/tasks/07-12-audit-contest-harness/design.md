# 审查设计

## 权威来源边界

1. 根来源为用户指定的 `FoLeaf/contest2026_004_TeamFalcons` 仓库 `dev-ai-contest-2026` 分支 README。
2. 记录分支解析出的提交 SHA，审查引用尽量固定到该提交或对应 `open-vela/docs` 分支当时的提交，避免浮动分支造成不可复现。
3. 阅读根 README 的全部唯一直接链接：三份通用规则、三个赛道导航、仓内 `logs/README.md` 和 CLA 页面。
4. 导航页只继续跟进两类链接：明确标注为赛道规则/要求的页面，以及被 harness 用来支撑具体断言的页面。普通安装教程、示例代码和外部资源不做无限递归审查，但会列入“已发现、未作为规则来源”的清单。
5. 本地 `BOUNDARY.md`、`CLAUDE.md`、`harness/README.md` 仅作为被审对象或辅助线索，不能充当官方规则证据。

## 审查模型

将 harness 每个结果分支整理为规则矩阵：

| 字段 | 含义 |
|---|---|
| Check | 函数及文件行号 |
| Harness claim | 实际断言、PASS/WARN/FAIL 条件 |
| Source | 官方文档和原文位置 |
| Authority | 强制要求、建议、教程约定、无依据 |
| Fidelity | 准确、部分准确、错误、不可自动判定 |
| Risk | 误报、漏报、绕过、维护风险 |
| Recommendation | 保留、降级、改写、删除或新增 |

## 严重级别

- Critical：可能导致违反官方硬性规则或提交无效，而 harness 未拦截或给出相反结论。
- High：把非官方条件作为提交门禁，或官方硬性项存在明显漏检。
- Medium：检查逻辑易误报/漏报，但通常可人工发现。
- Low：来源、措辞、可维护性或诊断质量问题。

## 验证边界

- 运行 harness 默认模式、`--strict` 和 `--json`，观察当前仓库的真实行为。
- 通过临时目录或内存级最小夹具验证高风险分支；不修改产品文件和真实日志。
- 报告同时给出“日常提示工具”和“最终提交门禁”两个适用性结论。

## 输出

审查结果写入任务目录的 `review.md`，包括来源清单、规则矩阵、按严重级别排序的发现、合理检查项、遗漏项和总体结论。

## 审查后处置（用户批准）

- 删除 `contest_flow_check.py` 及其自述、旧审查文件，不创建替代竞赛检查脚本；保留同目录中无关的 QSPI 检查工具。
- `docs/agents/BOUNDARY.md` 是唯一长期竞赛边界正文；官方远程文档始终拥有更高优先级。
- `CLAUDE.md` 只作为 Agent 入口，链接 `BOUNDARY.md`，不重复维护竞赛规则列表。
- `README.md` 作为作品说明，只链接边界文档并给出官方日志验证命令。
- 可自动验证的日志格式直接调用官方 `../.claude/skills/contest-log-collector/tools/validate-log.py logs/`；其余规则使用文档清单和人工证据，不再声称“一键合规”。
