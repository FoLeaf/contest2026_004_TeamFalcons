# VelaGuard MQTT 候选接入协议草案 v0.1

日期：2026-10-18。状态：设计草案，代码、主题、鉴权及界面均未实现或板验。

用户选择MQTT传输候选，板端状态栏显示远控中；异常与恢复由开发助手设计。最近一次修改的版本按最新编辑的候选理解，具体版本号由任务维护。用户未取消人工本地确认。本设计保留该步骤，与 [ADR 0007](adr/0007-mqtt-candidate-import-with-local-confirmation.md) 配套。

## 1. 范围与现状

手机通过受鉴权的HTTPS接口一次提交PDF和从机地址；云侧提取候选，通过MQTT发送到绑定的网关。板端确定性服务负责校验、合并预览、试读和本地确认，板载Agent不参与配置。

当前固件只有四类MQTT上报，没有候选下行订阅。新增接口实施前仍按 [NSH协议](velaguard-host-nsh-protocol.md) 操作。当前NSH的人工确认由操作流程与 `--confirm` 参数共同表达，固件尚不检查是否试读过及试读对应哪个版本；不能把本设计写成既有能力。

本次只定义候选配置通道。PDF原件、AI请求响应、语音和音频不走这些主题。MQTT不提供apply、confirm、NSH字符串或寄存器写入指令。

## 2. 连接与权限

- 远程候选接入使用MQTT over TLS，校验Broker身份；每设备独立凭证与ACL。现有公网1883明文链路不开放候选接入。
- 受控局域网可在显式测试构建中验证协议，使用测试凭证和真实人工确认，不把测试配置当作远程交付。
- 手机不持有设备或服务端Broker凭证。云侧先校验用户与网关绑定，再由专用配置服务发布；云侧LLM只输出数据，不能直接访问Broker。
- 设备只订阅自己命名空间的配置请求，只发布自己的配置状态；配置服务具有经用户绑定授权的设备范围，遥测看板保持只读。
- ACL隔离请求与状态方向。payload中的设备或用户标识不能代替身份认证；完整凭证不进入消息、界面或日志。

## 3. 主题与关联字段

根路径沿用 `vg/{device_id}`。新增两个主题均为QoS 1、retained=false；设备拒绝收到的retained配置请求。PUBACK只代表消息传输确认，手机必须依据板端状态判断结果。

| 主题 | 方向 | 用途 |
|---|---|---|
| `config/request` | 配置服务→板端 | open、put、test、cancel、query |
| `config/state` | 板端→配置服务 | 受理、拒绝、试读结果、等待确认及最终状态 |

所有消息包含 `schema_version=1`、`device_id`、`req_id`、`task_id`、`op`。`req_id`、`task_id` 为不超过64字节的ASCII标识。未知版本、未知操作或多余的执行字段直接拒绝，不解释为shell命令。

open请求必须关联当前设备 `boot_id`。设备验证无其他配置会话后生成随机、不可复用的 `session_id`，返回当前已确认表的 `base_hash`、当前候选revision和租约。其余请求必须携带同一 `boot_id`、`session_id`；设备重新启动后旧会话全部失效。session_id仅作关联与防重放，不代替TLS/ACL。

设备不接受open请求携带候选内容。重连先query当前任务，核对boot_id和租约，禁止自动重放旧候选。open重复请求必须返回原会话或已结束结果，不延长租约或新建会话。

状态额外包含 `state_seq`、`revision`、`candidate_hash`、`base_hash`、`test_id`、`state`、`error_code`、`retryable`、`uptime_ms` 和 `time_quality`；尚未产生的字段为null。`state_seq`在会话内单调递增，云侧丢弃较旧状态，终态不被晚到的等待状态覆盖。

### 候选put

- 第一次put要求 `revision=1`、`expected_revision=0`；后续每次完整替换候选要求 `revision=当前revision+1`，并携带 `expected_revision=当前revision`。新版本必须重新发送完整候选，不发送局部修改指令。
- 最近一次修改以板端受理的revision为准，不按消息到达顺序、墙上时间或文件修改时间猜测。并发编辑只有一份能通过expected_revision检查。
- 接收、验证、写入候选成功后才推进revision。旧版、跳号、版本冲突不覆盖当前候选；相同req_id和相同内容返回原结果，相同req_id但不同内容拒绝。
- 初版仅支持新增设备。以base_hash指向的完整已确认表为基础合并，保留现有点位；已有从机地址、重复点位id、空新增表、超过32点或能力不支持均拒绝。修改已有设备和清空运行表仍留给原NSH流程。
- 每点保留名称、FC、原文地址与协议地址、数量、类型、倍率、偏移、单位、PDF标识、型号、页码、原文依据。没有偏移时显式为0。仅接受实际固件支持的字段组合；当前仅int16/uint16，不支持的32位、浮点、字序或非零偏移不得静默降级。
- 测量范围不自动生成告警阈值；阈值只来自用户显式输入，界面标明来源。总线保持9600，地址与参数不匹配直接报错，不自动扫描或改地址。

### 内容摘要

请求中的 `candidate_json` 是UTF-8 JSON字符串，`payload_sha256`针对该字符串解码后得到的原始UTF-8字节计算，包含点位及来源。设备核验后解析，并保留同一原始字节串供审计；不依赖两端JSON重排后能产生相同摘要。

设备将合并后的完整运行表序列化，生成 `candidate_hash`，并保存这份确定的待提交内容。`base_hash`指向当前持久化运行表的原始字节摘要。test与本地确认同时绑定revision、payload_sha256、candidate_hash和base_hash，避免既有表变化造成覆盖。

## 4. 状态、试读与本地确认

主流程：`opened → candidate_ready → testing → awaiting_local_confirm → committing → applied`。失败分别返回可重试的原状态或终态failed；取消与租约超时进入cancelled或expired。

1. 只有test请求引用当前revision和candidate_hash时才开始；使用既有总线锁、读功能码和固定9600，对全部新增点位试读，保留既有采集。总线操作有界，不在MQTT接收回调中执行。
2. 板端生成test_id，记录每点原始值、工程值、单位、采样时间、错误，以及上述版本/摘要。部分失败仍展示所有结果，但初版只有全部新增点位成功才进入等待确认。
3. 任何候选内容、阈值、来源或已确认表变化均使试读和确认失效。testing、等待确认时收到有效新版put，旧test_id立即失效；旧试读稍后完成也不得覆盖新版状态。若原已确认表变化，任务结束并要求重新open。
4. 板端预览展示目标设备、新增/保留点位、手册页码、试读值和失败项。确认按钮只绑定屏幕正在展示的revision、candidate_hash和test_id，不读取另一个可变的最新候选。
5. 用户在板端按确认添加，确定性代码在提交互斥区重新校验会话、租约、base_hash、版本及试读有效期，成功落盘后才更新内存/代次、通知MQTT并进入applied。两次点击只提交一次。
6. 不接受任何MQTT确认指令。手机上传、云侧解析、状态栏显示远控中、ASR文本或Agent输出均不能替代上述操作。板端取消始终可用。

状态栏在open受理后显示远控中，点击进入当前任务详情，并显示目标从机、候选版本及阶段；等待时补充待本地确认。该提示只表示远程配置会话存在，不赋予云侧其他控制权限。结束或租约失效后恢复普通状态；告警提示优先，远控标记不得遮挡告警。

## 5. 上限、失败与恢复

以下是首版建议预算，实施时必须测量内存、MQTT收包与界面表现后确认，当前不宣称固件已支持。

- 单网关仅1个配置会话；同时保留最多1份活动候选和1份正在退场的试读结果。任一配置请求的完整UTF-8 payload不超过16KiB，每页试读结果状态不超过4KiB，拆页带test_id、page、page_count，缺页时手机不显示结果完整。
- 候选合并后最多32点；具体字段限制取现有点表校验器与新增传输限制的较小值，不截断字段。原文过长时云侧要求精简引用，不在板端自动截断。
- 会话租约10分钟，以板端单调时钟计时且不自动延长；试读结果有效期2分钟。租约或试读过期必须重新执行相应步骤。
- 单会话最多32个不同req_id，最多3次完整试读；状态query每秒最多1次，越限不执行操作。缓存本会话请求摘要和结果，重复请求不重复I/O。终态保留用于查询，直到新会话建立；更早会话返回unknown_task，不重执行。
- BUSY时云侧间隔1、2、4秒最多重试3次；同req_id重传只获取原结果，明确可重试错误后的新尝试使用新req_id。试读仍服从租约和次数预算，禁止无限重试。

| 情况 | 处理 |
|---|---|
| 错网关、鉴权失败、旧boot/session、retained消息 | 拒绝，不写候选、不试读；返回或记录相应错误，避免回传敏感内容 |
| 旧revision、重复请求、迟到试读或状态 | 返回当前状态或原请求结果；内容冲突报revision_conflict/req_conflict，不覆盖新版 |
| 缺必要字段、不支持格式、地址冲突、容量不足 | 返回具体点位和原因；原运行表及已受理候选不变 |
| 总线忙、试读超时、部分失败 | 展示失败项，禁用确认；释放总线锁，允许在预算内重新test |
| MQTT断线或取消发生在提交开始前 | 取消等待确认权限，使test_id失效；保留运行表。重连需重新open或query终态，不能自动恢复确认 |
| 取消、租约过期与确认并发 | 在同一状态锁下决定顺序；进入committing前可取消，之后返回too_late并查询实际提交结果 |
| 落盘失败或空间不足 | 不切换内存表，不报applied；进入failed，返回storage_error并按存储层实际恢复结果报警 |
| 已进入committing后断网 | 完成或失败由板端确定；网络恢复query实际终态，不能因超时再次提交 |
| 板端重启 | 旧会话和试读一律失效，先校验持久化运行表；只能报告实际加载结果，不能凭云侧已发送状态补报成功 |

applied终态回执包含新运行表hash。确认前先保存有界提交记录（task/session/revision/预期表hash），启动后对照实际运行表；记录丢失、损坏或表不完整时返回recovery_unknown并要求核对，不盲目补交。此记录不等同于FAT掉电原子性或完整双槽保护，异常恢复必须板验。

## 6. 与NSH共存

新增接口实施前NSH不变：试读展示后停下来等人，再单独发送apply。现行NSH没有试读版本强制检查。

实施远程接入时必须同步增加所有配置入口的会话互斥。远控会话活动期间，NSH候选编辑、试读、apply、abort与扫描生成候选返回明确busy，不共享文件覆盖候选；已确认表查询继续可用。NSH存在未结束候选时拒绝远程open，不删除该候选。板端本地取消远程会话后才允许切回NSH。

远程候选使用独立的受保护存储，原NSH apply不得读取它。NSH锁检查与提交必须处在同一临界区，避免先检查后提交的竞争。板载Agent对两条入口都没有访问权限。

## 7. 后续实施与验收

先实现主机侧状态机与协议校验，再接入MQTTS收包/权限、后台配置服务与板端预览确认；板测中的现有固件不因本文而变化。手机及云侧可先使用明确标注的模拟器联调。

必须覆盖：完整新增、未确认/取消不生效、重复/乱序消息、候选修改使旧试读失效、部分失败、错网关、超限、NSH竞争、断网/租约过期、落盘失败、确认与取消竞争、重启后核对实际运行表。运行采集、告警、界面与MQTT已确认表必须一致，并验证云侧及Agent均无法代确认。
