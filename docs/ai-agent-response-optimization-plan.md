# ai_agent 响应链路优化计划

日期：2026-10-19。状态：用户已选为下一阶段，本次完成规划，实施与真机验收尚未开始。

## 目标与范围

让自然语言只读查数具备可解释、可测量的响应时间，定位并减少主要等待，同时保持数据真实、工具权限和本地采集。沿用板载 ai_agent / llm_proxy 经 HTTPS 直连 MiMo；后续手机语音复用此链路，本阶段不开发语音、候选配置或 OTA。

QA-04 冻结仍未定位。本阶段响应优化通过不能关闭 QA-04，也不能替代整机长期稳定性验收。上轮停止烧录、复位和重跑的决定仍适用于已结束的诊断轮；本次仅规划，后续板测在明确启动本阶段实施后按板端内环执行。

源码核对：`packages/ai_agent/src/core/agent_loop.c` 在 `llm_chat_tools()` 前后计时，随后才执行工具。因此 `tool=vg_run_report latency=97100ms` 是该轮 LLM 调用耗时。历史报告文档将它写成工具耗时有误，以此说明和源码为准。`llm_ms` 包含本地请求处理、网络和远端等待，不能直接解释成模型推理时间。整轮 elapsed 使用墙上时间，性能验收须改用单调时钟，避免校时干扰。

`infra/vela_tls.c` 已有连接池及失效重连；不能把新增连接池当作默认优化。已有记录包含 DNS 和 socket 创建失败，须实测连接复用及资源回收。当前证据缺少分段时间、同请求主机对照和首字节时间，无法确定远端或板端主因。

## 执行顺序

每一步完成后形成可审阅的结果，按证据决定下一项改动，避免同时改变多个变量。

| 步骤 | 工作 | 完成条件 |
|---|---|---|
| RSP-01 分段计时 | 在真实请求路径加入低开销计时；核对固件、端点和模型配置；更正工具耗时误读 | 正常、失败、重试路径均有完整时序；不记录密钥或完整请求正文；形成基线 |
| RSP-02 同请求对照 | 板端与电脑在相近时段、同出口网络交替请求同一服务；分别测试新连接与复用连接 | 给出各段耗时、请求轮数、成功率和证据局限；明确首要优化对象 |
| RSP-03 定向优化 | 每次仅改一个主要因素，以相同测试集作前后比较 | 延迟改善可重复，回答正确率、采集和资源占用不退化 |
| RSP-04 交互与失败恢复 | 检查受理反馈、工具阶段提示、整轮期限、迟到结果隔离；有依据再做流式输出 | 等待状态准确，错误有明确结果，失败后可接受下一请求，旧结果不覆盖新轮次 |
| RSP-05 自然语言查数验收 | 当前值、离线列表、近期告警与运行摘要；无数据或过期数据如实说明 | 实测报告与原始证据入库，达到目标或明确记录未达项 |

## RSP-01：测量合同

以单调时钟记录请求受理到最终答案可见的时间，关联 round_id、LLM iteration、HTTP attempt。每次尝试分别记录：

1. 排队与请求构造时间、请求字节数。
2. 网络资源及连接池等待、DNS、TCP 连接、TLS 握手；复用时标明 reused，未执行的阶段标为不适用。
3. 请求发送完成、首个响应字节、响应体收完、JSON 解析完成。
4. 每个工具实际执行起止、工具名、结果大小及返回状态。
5. 重试原因与退避时间、HTTP 状态、最终状态、总轮数；如服务返回 usage，仅记录计数。
6. UI 受理反馈和最终答案可见时刻、堆内存变化及网络资源回收情况。

阶段定义须避免重复累计。首次响应字节可能只是 HTTP 头，不能冒充首个可见文本。非流式路径暂不声称测到模型首 token。若底层接口暂时只能测 DNS+TCP 总和，明确标成组合阶段，不填推测值；确认该段占主要时间后再拆分底层实现。计时输出不得包含 Authorization、API key、MQTT token 或完整业务数据。

## RSP-02：对照方法

固定问题、系统提示、工具定义、消息历史、模型及输出预算；工具结果使用同一脱敏快照，记录请求摘要及字节数。电脑请求仅用于开发诊断，正式产品仍由板端调用工具和后端。

先做每组 3 次探索，再对主要场景各做至少 10 次基线和优化后样本，交替采样降低时间段偏差；冷连接、复用连接分别统计。基线覆盖简单短答、单点查询、运行摘要；验收增加离线列表及近期告警。记录中位数、最大值、成功/失败数和各段占比；10 次样本不宣称可靠 P95。需要 P95 时另安排至少 50 次样本并注明样本量。

电脑慢且板端在相同等待阶段慢，只能提示服务或共同网络出口因素；板端 DNS/TLS/发送明显慢则优先查板端网络栈、连接复用与资源。服务端排队和推理的准确区分需服务端时间指标，客户端首字节不足以单独证明。工具耗时高则检查快照锁、文件访问与串行等待。

凭证只从已授权的受保护来源读取，不为测试从板端导出密钥；缺少主机可用凭证时先完成板端分段测量，对照项标为待提供条件。

## RSP-03：按瓶颈选择改动

- 连接建立占比高：修正实际连接复用、失效连接回收、DNS/连接超时；TLS 校验保持有效，不以关闭校验提速。
- 首字节等待高：先核对服务官方支持的推理模式、输出预算和限流行为，按接口能力进行单变量对比；模型变更必须同时验证中文理解和工具选择质量。
- 请求构造或内容过大：精简重复系统提示、无关历史及不需要的工具定义，保留权限约束和必要证据。
- ReAct 轮数多：减少重复工具调用，优先让已有只读快照工具一次返回必要信息；保留查数真实性。实时点值不得复用无新鲜度与配置版本约束的历史回答缓存。
- 工具或显示耗时高：分别优化确定性工具及 UI 更新路径。流式输出仅在服务支持、板端内存及分片解析验证通过后引入，区分改善首段可见时间与降低整轮时间。

超时采用整轮剩余预算，避免重试、退避和多轮请求各自叠满上限；不得仅缩短 socket timeout 将慢成功转换成大量失败。具体预算由基线和交互目标决定。

## 目标与验收

以下为本阶段暂定工程目标，不是已实现能力或服务性能承诺。完成 RSP-02 后结合实测确认可达性，调整时记录依据。

| 指标 | 暂定目标 |
|---|---|
| 用户操作受理反馈 | 1 秒内可见 |
| 正常网络下单点查询最终答案 | 中位数不超过 15 秒，10 次样本最大值不超过 30 秒 |
| 运行摘要最终答案 | 中位数不超过 30 秒，10 次样本最大值不超过 60 秒 |
| 正确性 | 固定测试集的数值、单位、点位、在线状态与工具快照一致；缺失、过期数据明确说明 |
| 相对改善 | 与同条件基线比较；如目标未达，给出瓶颈分段证据，不仅报告平均速度 |
| 本地功能 | 请求前后及处理中采集计数持续增长；告警和 UI 继续工作；不出现与请求相关的新超时或内存持续增长 |
| 失败恢复 | 覆盖解析失败、网络超时、429、连接失效；有界结束，资源释放，后续正常请求成功，迟到结果隔离 |

主机回归覆盖计时、超时及解析的实际分支；板端短测证明真实链路。出现冻结则保存证据并将该次记为中断，不强行归因为本阶段，也不在本阶段展开 QA-04 根因修复或自动开启 24 小时长测。

## 改动归属与交付

公共框架改动在 `packages/ai_agent` 的实际 checkout 功能分支；若需 NuttX 网络实现改动，另在其功能分支最小修改。应用、配置、测试脚本和验收文档在竞赛仓。遵守各仓现行规则及适用的板端验收 skill。

交付包含分段计时实现、可重复对照脚本、脱敏基线/优化后记录、正确性与失败恢复结果、多仓提交和固件摘要。每项完成后提交本项改动；日志原文不重写，推送和 PR 按用户授权执行。
