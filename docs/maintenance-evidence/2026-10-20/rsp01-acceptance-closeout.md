## 一、响应结束判定

### 缺陷

`tls_read_response()` 与 `vela_http_post_json()` 的响应体循环只认
`Content-Length`。chunked 响应没有该头，在 keep-alive 连接上读完终止块
后继续读，直到 socket 超时。

### 修复与主机实测

新增 `src/infra/http_body.h`，按 RFC 9112 6.3 判定结束条件。把未改动的
`vela_tls.c` 编到主机链接 mbedtls 3.4.0，对本地可控 TLS 服务逐用例测试
（每用例独立进程，避免连接池串扰，socket 超时设为 5 秒以便区分）：

| 用例 | 耗时 | 结果 |
|---|---|---|
| Content-Length 完整 | 0.094s | 立即返回 |
| chunked 完整 | 0.094s | 立即返回，解码 20 字节正确 |
| chunked 分两次到达 | 0.895s | 等于服务端发送间隔 |
| 连接关闭 | 0.094s | 立即返回 |
| Content-Length 截断 | 5.1s | 等满超时，符合预期 |
| chunked 截断 | 5.1s | 等满超时，符合预期 |
| 无分帧 keep-alive | 5.1s | 只能等超时，符合预期 |

`tests/test_http_body.c` 覆盖 10 组判定用例。

### 与板上长等待的关系：没有

板上重新采集后长 `body` 仍出现，且未触发新增的"无长度信息"警告，说明
真实服务发送了 `Content-Length`。**上一轮把 84 秒归因于分帧是错的，这里
更正。** 缺陷真实存在且已修复，但不是板上长等待的原因。

## 二、失败请求的计时覆盖

### 缺陷

`tls_ctx_connect()` 只在连接**成功**时记录 `dns_tcp_ms`。失败时直接
`return`，连接耗时不计入任何阶段，只体现在 `http` 总时长里。实测偏差：

```
修复前：dns_tcp=na ... ttfb=na body=na ... http=81580
修复后：dns_tcp=30 ... ttfb=na body=na ... http=660
```

同一缺陷在握手失败和 RNG 初始化失败路径上同样存在，一并修复。失败路径
现在都先记录时间再看返回值：一次失败的连接仍然是一次被测量的连接。

### 顺带修复

`llm_proxy.h` 使用 `agent_llm_timing_t` 却没有包含
`infra/agent_timing.h`，头文件不独立，单独包含时编译失败。

### 阶段与总时长对应（本轮实测）

用 `chain4` 记录逐条核对，五个请求全部对应：

| 阶段和 | http 总时长 | total | 占比 |
|---|---|---|---|
| 161160ms | 161170ms | 161180ms | 100% |
| 660ms | 660ms | 670ms | 99% |
| 660ms | 660ms | 670ms | 99% |
| 7240ms | 7250ms | 7260ms | 100% |
| 10020ms | 10130ms | 10140ms | 99% |

差额是各阶段之间的取整与 `agent_lap_ms` 之间的间隙，在 10ms 分辨率下
属于正常。**每一毫秒都有归属。**

## 三、同一次运行内的证据链

脚本 `scripts/serial_rsp01_chain.ps1`，一次会话内四步，中间不重启。

`chain4` 结果：

| 步骤 | 结果 | 关键读数 |
|---|---|---|
| 基线请求 | 触发 120 秒看门狗 | `ttfb=8040 body=152320 http=161170` |
| 受控失败 | 按预期失败 | `dns_tcp=30 tls=570 http=660 rc=-1`，670ms 返回 |
| 恢复端点 | 成功 | `Backend 0 configured: token-plan-cn...` |
| 恢复后请求 | **成功** | `END status=ok iters=2 llm_ms=17420 elapsed_ms=18990` |

### 基线那次为什么是 timeout

服务端返回了 152 KB 响应体，生成耗时 152 秒，超过 `AGENT_LLM_TIMEOUT_SEC`
的 120 秒，被看门狗判为超时。计时行完整记录了这段时间：`body=152320`
与 `http=161170` 对得上，说明等待发生在等响应体，不是连接或解析。
这不是固件缺陷，但说明超长响应会稳定触发看门狗，值得在 RSP-03 关注。

### Agent 状态与资源释放

- 失败后 Agent 继续接受请求，恢复后请求成功，说明连接池槽位与响应缓冲
  已释放
- 失败请求 `pool=60`：等待连接池槽位 60ms，说明上一个轮次（板端自行发起
  的告警建议）还占着槽位，之后正常归还
- 全程未出现新的内存告警或分配失败

## 四、429 重试

### 方式

主机可控服务 `server429.py`（明文 HTTP，端口 9444）。固件按端口选择传输
方式——只有 443 走 TLS，因此测试服务必须说明文 HTTP 才能驱动同一个重试
循环。凭据为假值，服务端不校验。

### 场景 A：两次 429 后成功

```
客户端：attempt=3 backoff=4000 llm_total=6004 status=200 parse_ok=1 rc=0
服务端：#1 /429-then-ok
        #2 /429-then-ok (+2.00s)
        #3 /429-then-ok (+4.00s)
```

服务端独立观测到的间隔与 `AGENT_LLM_RETRY_BASE_SEC << (retry-1)` 完全
一致：首次重试前 2 秒，第二次前 4 秒。最终拿到 200 并解析成功。

### 场景 B：持续 429

```
客户端：attempt=4 backoff=8000 llm_total=14005 status=429 parse_ok=0 rc=-1
服务端：#4〜#7 /429-always，间隔 +2.00s +4.00s +8.00s
```

共 4 次尝试（`AGENT_LLM_MAX_RETRIES=3` 加首次），退避 2/4/8 秒，14 秒后
有界退出，`rc=-1`、`status=429`。没有挂死，没有无限重试。

## 五、板端网络故障现场

见 [网络故障现场](rsp01-network-fault-scene.md)。要点：

- 链路、ARP、主机到板方向均正常
- 直接原因：Windows ICS 的 `SharedAccess` 服务在运行，但 **UDP 67 无任何
  监听**，DHCP 不提供租约，板端 IP 退回 `0.0.0.0`
- 恢复由用户重开共享完成，不是固件改动
- 恢复后 `dns_tcp=50 tls=450 status=200`，链路完全可用

## 六、待修缺陷：连接失败耗时

修复计时覆盖后，同一失败请求从 81 秒降到 670ms——但后者是**端点有响应
并立即拒绝**的情形。真正无响应的连接仍会等待：

```
主机实测 203.0.113.1（TEST-NET-3）：
status=-2 wall=5.16s dns_tcp=1 tls=5156
phases sum=5157 ms of wall 5157 ms
```

`mbedtls_net_connect()` 用阻塞 connect，没有超时，SYN 重传耗尽才返回。
板上 `CONFIG_NET_TCP_MAXRTX=8`，退避累加到约 81 秒。

**本轮不修**。两个方向都超出验收收尾范围：调整全局重传参数会影响所有
TCP 连接；改非阻塞 connect 属于 RSP-03 连接层改动。作为待修缺陷保留。
