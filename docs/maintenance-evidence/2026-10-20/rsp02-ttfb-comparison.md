# RSP-02：正常请求 body 等待的归因

日期：2026-10-20。状态：完成对照测量，首字节等待归因于服务端；单一优化因素已选定并复测。

固件 SHA256 `73a7e1ecc7bfa566d29b75e422988015f94228f863bedd7fb01a908f9df63dd9`
（含响应组成与接收进度插桩）。端点 `token-plan-cn.xiaomimimo.com`，模型
`mimo-v2.5`。

## 测量条件

| 项 | 值 |
|---|---|
| 从站 | **离线**，总线成功 0%（0/860） |

## 一、板端与电脑端首字节对比

板端 12 次请求与电脑端 12 次请求的 `ttfb` 分布：

| 端 | 低档 | 主档 |
|---|---|---|
| 板端 | 1960 2040 2620 2760 3660 3820 | **8010 8020 8060 8060 8070 8070 8090** |
| 电脑 | 1953 2409 3124 3416 4375 5082 | **8077 8090 8096 8099 8106 8113 8117 8127 8140** |

两端形态一致：大部分请求落在 8.05-8.14 秒的窄区间，少数落在更低的档位。
两端共享同一出口与同一服务，**首字节等待在服务端，不在板端**。

电脑端主档的离散度只有 ±30ms。模型每次生成的 token 数不同，推理时间不会
如此稳定；这是服务端的固定调度窗口。

## 二、本地服务对照

为排除"板端网络栈慢"这一可能，用同一台机器上的本地 TLS 服务作对照：

```
本地服务（127.0.0.1:9446，立即应答）：ttfb=0ms   total=50ms
远程服务（token-plan-cn）        ：ttfb=8098ms
```

同一台电脑、同一条出网链路，只换服务端。8 秒随服务端出现，不随网络路径
出现。

## 三、请求参数对首字节的影响

在电脑端逐项改变请求，其余条件不变：

| 变化 | ttfb |
|---|---|
| 基线（`max_completion_tokens=16384`） | 8116ms |
| 去掉 system prompt | 3184ms |
| `max_completion_tokens=256` | 2729ms |
| 去掉 `max_completion_tokens` | 8091ms |
| 加 `Connection: keep-alive` | 8115ms |

初看"去掉 system prompt 快很多"，于是做了 8 轮交替 A/B：

```
no-system  : 3124 8099 1953 3416 2409 4375 5082 8114
with-system: 2196 3414 4471 2772 8092 5776 8091 3476
median no-system=3896ms   with-system=3974ms   diff=+78ms
```

**差值 78ms 落在噪声内，system prompt 不是因素。** 交替采样是为了让时间段
漂移同样作用于两组；单次对比得出的 5 秒差异是抽样错觉。

补充采样 12 次无 system prompt 的请求，9 次仍落在 8077-8140ms。

**结论：请求参数改变不了这 8 秒。**

## 四、接收进度：body 等待是什么形态

板端新加的接收进度记录，会记录两次读之间超过 1 秒的间隙。一次典型记录：

```
body progress: gaps=5 first_read=13060ms total=3658 bytes
body gap 1: idle=13060ms at=13060ms bytes=12
body gap 2: idle=5000ms  at=18060ms bytes=18
body gap 3: idle=5000ms  at=23060ms bytes=24
body gap 4: idle=5000ms  at=28060ms bytes=30
body gap 5: idle=1350ms  at=29410ms bytes=3653
```

形态是**长时间无数据、每 5 秒多 6 字节、最后一次性到齐**，不是持续缓慢
到达。全部样本中 `idle=5000ms` 出现 10 次，累计字节每次精确增加 6。

6 字节正是一个一字节 chunk 的编码开销（`1\r\nX\r\n`），即服务端在生成期间
每 5 秒发一个占位块保持连接。这些块不含回答内容。

用本地可控服务按同样节奏发送，可以完整复现：

```
本地心跳服务：wall=20.05s ttfb=0ms body=20002ms resp_bytes=3439
```

与板端现象一致，说明这就是该现象的全部机制。

## 五、152KB 响应的组成

需要更正上一轮的读法：`body=152320` 是**毫秒**，不是字节。上一轮把它当成
响应体大小是错的。

该次请求的实际读数是：

```
http ... ttfb=8040 body=152320 ... total=161180
[llm] Response: 54 bytes text, 2 tool calls, finish=tool_calls
```

响应解析结果只有 54 字节文本与 2 个工具调用，但 body 阶段占了 152 秒。
它不慢在数据量，慢在**等数据**。该次请求超过 120 秒看门狗后终止，所以没有
`Resp bytes` 组成行。

新插桩记录的响应组成显示，实际响应体一直很小：

| resp 字节 | text | reasoning | toolargs | completion |
|---|---|---|---|---|
| 651 | 152 | 48 | 0 | 51 |
| 919 | 0 | 84 | 56 | 70 |
| 2016 | 783 | 757 | 0 | 426 |
| 2684 | 0 | 171 | 1874 | 744 |
| 3621 | 0 | 833 | 2139 | 928 |

**响应体在 0.6-3.6 KB 之间，其中工具参数与 reasoning 占大头，可见文本很小。**
所谓"152KB 响应"不存在，那是把毫秒当成了字节。

## 六、选定并复测的单一因素

对照后只有一个因素同时满足"证据强、可复现、可量化"：

**服务端首字节固定延迟约 8.1 秒，与请求内容和连接复用无关。**

复测证据：

| 条件 | 结果 |
|---|---|
| 板端 12 次 | 7 次在 8010-8090ms |
| 电脑端 12 次 | 9 次在 8077-8140ms |
| 本地服务 | 0ms |
| 改提示词 | 无变化（A/B 差 78ms） |
| 改输出预算 | 无变化 |
| 改连接头 | 无变化 |
| 复用连接 | 仍出现 8 秒档 |

这不是可以在板端消除的延迟。本轮**不据此做代码优化**：唯一的收益方式是
让等待可见（属于 RSP-04 的受理反馈）或减少请求次数（属于 ReAct 轮数
问题），都不在本轮范围。

## 七、连带发现

1. 板端正常请求的 `body` 阶段包含服务端 5 秒心跳占位，`body_ms` 因此显著
   大于实际数据传输时间。理解这个数字时需要知道它测量的是"等到响应体
   收完"，不是"传输耗时"。
2. 复用连接不缩短首字节，说明连接建立不是瓶颈。这一点与 RSP-01 的结论
   一致。
3. 从站离线时 `vg_point_read` 返回离线状态，长报告的生成路径仍会走
   `write_file`，与本轮计时无关。
